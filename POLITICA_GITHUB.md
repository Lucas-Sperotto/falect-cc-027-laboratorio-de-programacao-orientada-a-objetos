# Política de GitHub da Disciplina

## 1. Finalidade

O GitHub é o ambiente oficial de organização, desenvolvimento, versionamento e acompanhamento técnico das atividades da disciplina. O SIGAA permanece como ambiente institucional de registro formal da entrega e da nota.

## 2. Regra geral de entrega

Cada atividade deverá ter:

- desenvolvimento e histórico no GitHub;
- entrega técnica por repositório e, quando solicitado, por `Pull Request`;
- registro formal no SIGAA por meio de relatório curto em PDF com os links necessários.

## 3. Conta, acesso e identificação

Cada estudante deverá:

- possuir conta no GitHub;
- manter perfil minimamente identificável;
- acessar o repositório oficial da disciplina;
- realizar `fork` do repositório da atividade;
- clonar o repositório `forkado` localmente, preferencialmente no VS Code.

## 4. Fluxo padrão de trabalho

O fluxo padrão da disciplina será o `Forking Workflow`, adotado como prática obrigatória nas atividades de laboratório e nas entregas versionadas.

### Etapas

1. acessar o repositório oficial da disciplina;
2. realizar `fork` do repositório da atividade;
3. clonar o `fork` para a máquina local;
4. criar uma `branch` específica para a atividade;
5. desenvolver, testar e documentar;
6. registrar `commits` frequentes e coerentes;
7. enviar a `branch` para o GitHub com `push`;
8. abrir `Pull Request` quando a atividade assim exigir;
9. registrar a entrega no SIGAA por relatório em PDF com os links necessários.

## 5. Padrões mínimos de nome

### Pastas de atividades

- `lista-01`
- `laboratorio-01`
- `projeto-integrador`
- `projeto-etapa-01`

### Branches

- `atividade/lista-01`
- `atividade/laboratorio-01`
- `projeto/etapa-01`
- `correcao/ajuste-leitura-arquivo`

### Commits

Adotar mensagens curtas, claras e consistentes. Exemplos:

- `feat: implementa leitura de vetor`
- `fix: corrige condição do laço`
- `docs: adiciona instruções de execução`
- `refactor: reorganiza funções do menu`
- `test: adiciona casos de teste para fila`

## 6. Organização mínima de cada atividade

Cada entrega deve conter, quando aplicável:

- `README.md` explicando o que foi feito;
- código-fonte organizado;
- instruções de compilação, execução ou uso;
- identificação do autor;
- arquivos necessários para avaliação.

Quando a atividade pedir documentação extra, o enunciado definirá a estrutura esperada.

## 7. Relatório curto para o SIGAA

O relatório em PDF para registro no SIGAA deve ser simples e objetivo. Em geral, ele deve conter:

- nome do estudante;
- disciplina;
- identificação da atividade;
- link do repositório;
- link do `Pull Request` ou do commit principal, quando houver;
- resumo curto do que foi desenvolvido;
- observação sobre uso de IA, quando a atividade exigir.

Há um modelo inicial em `templates/relatorio-sigaa.md`.

## 8. O que será observado pelo professor

O professor poderá observar:

- frequência e progressão dos commits;
- organização do repositório;
- clareza do código;
- qualidade da documentação;
- coerência entre histórico e resultado final;
- capacidade de explicar o que foi produzido.

Quantidade de comentários no código, isoladamente, não é critério. O critério é a qualidade da clareza técnica, da organização e da documentação.

## 9. Condutas não permitidas

Não é permitido:

- apagar histórico para esconder o processo;
- copiar integralmente repositórios de colegas;
- entregar código sem compreender;
- usar material de terceiros sem citação;
- abrir entrega sem relação com o trabalho efetivamente realizado.

## 10. Finalidade pedagógica

O objetivo do uso do GitHub não é apenas receber arquivos. O estudante deve aprender organização, versionamento, documentação, rastreabilidade e colaboração em um fluxo próximo ao contexto profissional.
